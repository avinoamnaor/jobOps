# JobOps — Guide for Claude Code

Personal, local, single-user job-application tracker. React + TypeScript (Vite)
frontend, Python + FastAPI + SQLAlchemy backend, PostgreSQL (Docker), Alembic.

## Architecture invariants (do not violate)

1. **Status is a cached projection of an append-only event log.** Exactly one
   service function assigns `applications.status`, and it always writes a
   `status_changed` event in the same transaction. Status changes go through
   `POST /applications/{id}/status` only — `PATCH` must never accept `status`.
2. **Documents are content-addressed and immutable.** Stored as
   `<sha256><ext>`. Never mutate a stored file, duplicate a Document row, or
   change a hash. An edited CV is a new document. Uploaded filenames are never
   used to build filesystem paths.
3. **Submitted-CV rule.** Submitted-state statuses (see
   `STATUSES_REQUIRING_SUBMITTED_CV`) require `submitted_cv_document_id`;
   `saved` and terminal/hold statuses do not. Enforced in the service layer.
4. **Layering.** Routers are thin (parse ↔ serialize); all business rules live
   in `services/`. Keep SQLAlchemy `models/` and Pydantic `schemas/` separate.
   The backend is the authoritative enforcement point — never rely on React
   for a rule.
5. **Migrations via Alembic only** (never `create_all`). Read every
   autogenerated migration; name FK/unique constraints explicitly (autogenerate
   emits unnamed constraints that break `downgrade()`).
6. **Config via `app/config.py` (pydantic-settings).** No module reads
   `os.environ` directly. Personal/local values live in `.env` only;
   `.env.example` stays generic and public-safe.

## How to run (Windows PowerShell)

- Postgres: `docker compose up -d` (data is in a named volume; `down -v` wipes it).
- Backend (from `backend/`): `.\.venv\Scripts\uvicorn.exe app.main:app --reload --port 8000`
- Migrations (from `backend/`): `.\.venv\Scripts\alembic.exe upgrade head`
- Frontend (from `frontend/`): `npm run dev` → http://localhost:5173
- The frontend must be on 5173 (backend CORS allows only that origin).

**Real vs demo mode:** a normal terminal runs **real mode** (`.env`, `jobops`
DB). Setting `JOBOPS_ENV_FILE=.env.demo` switches to demo data (`jobops_demo`)
and drops personal `.env` overrides. If a config/`.env` change "doesn't take",
you're likely in demo mode or relying on `--reload` (which does NOT watch
`.env` — restart the backend for env changes).

## Testing

- Backend: `.\.venv\Scripts\python.exe -m pytest` — runs against a real
  `jobops_test` DB built from the migrations; a conftest guard refuses any DB
  not named `jobops_test`.
- Backend lint: `.\.venv\Scripts\ruff.exe check app tests`
- Frontend: `npm run test` · `npm run lint` · `npm run build`
- Frontend type-check only: `npx tsc --noEmit -p tsconfig.app.json`
- E2E: `npm run test:e2e` (Playwright; own DB `jobops_e2e`, ports 8001/5174).

## Working style — default: FAST ITERATION

Unless asked for `/full-verify` or wrapping a major phase:
- Make only the requested change; no unrelated refactoring.
- Run only the most relevant targeted test(s); a lightweight `tsc --noEmit` if
  frontend changed. Do NOT auto-run full suites, Playwright, production build,
  or persistence/restart checks.
- Don't debug unrelated warnings/tooling unless they block the task.
- If a check fails on orchestration/tooling (not a real bug), report and STOP —
  don't build a workaround.
- Don't create temp scripts unless clearly necessary.
- **Default to real mode.** Use `.env.demo` only when explicitly asked for
  demo/screenshots, and never silently switch between real and demo data.
- If an `.env` change needs a backend restart to take effect, say so explicitly.
- **Never claim a test/check passed unless it actually completed successfully.**
- Personal names/paths/settings live only in local `.env` — never in committed
  source or `.env.example` (reinforces config invariant #6).

## Reporting & Git state

End every task with a short report: **what changed**, **what was actually
verified**, **anything not verified**, and **exact Git state only if relevant**.

When Git state matters, base the report on `git status --short` — not inference —
and use the terms precisely:
- `??` = **untracked** (not in Git at all yet).
- modified but not `git add`ed = **modified/unstaged**.
- **staged** = in the index after `git add`.
- **committed** = stored in local Git history (`git commit`).
- **pushed** = present on the remote.

Never describe a file as staged, committed, or pushed unless the actual Git
state confirms it. (`??` is untracked, not staged.)

## Gotchas

- `docker` is not on PATH inside Claude tool shells — use
  `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe`.
- The SQLAlchemy engine sets `connect_timeout=5`; keep it (without it a down DB
  hangs for minutes).
- On Windows, Playwright/uvicorn can leave orphan processes holding ports
  8000/8001/5173/5174 — clean them up after E2E.
